# The Haiku Tax

## Question

On realistic enterprise agent tasks, which closed or open-weight model gives the most successful tasks per dollar, and how far below the top closed tier is it?

## Status

Complete as a run, **results withheld**. The full grid ran on 2026-10-19 and 2026-10-20 (ten use cases, 100 test tasks each, 6 closed models and 16 open-weight model/provider pairs, one run per task, plus two pre-action-check arms). Recorded token spend at list prices: **$521.42**, including $39.62 of superseded runs and the development and smoke tests.

Three open models ran on part of the grid only, because an inference provider blocked the account mid-run.

## Results

**Withheld pending provider review.** The write-up is an internal draft. Open-weight models ran on two commercial inference providers, and the providers have not yet seen their numbers. Until they have, this repository publishes no per-model or per-provider result:

- no success rates, costs per success, latencies or failure counts;
- no per-task result rows;
- no results export (`results/haiku-tax.json`).

What is published: the nine harness environments, the task generators and graders, the agent runner, the grader-audit exclusions, the analysis code that produced the tables, and the method below. Anyone with API keys can rerun the benchmark from [RERUN.md](RERUN.md) and get their own numbers.

The sibling benchmark [model-swap-on-recorded-traffic](../model-swap-on-recorded-traffic) uses these full runs as ground truth and publishes only its step-level results.

### Method

**Use cases.** There are ten. Nine are in this directory (`envs/<name>/`). Each one has:

- a synthetic environment with 3-7 read tools and 1-4 write tools (writes are recorded and graded, never executed);
- a written policy the agent sees;
- 3-5 hidden prudence rules the agent never sees;
- a deterministic grader (no LLM judge anywhere);
- 132-168 tasks generated from a fixed seed.

The tenth use case (support tickets) ran on the SwapBench bank set through tau2-bench. It needs a private hidden split and is not included (see Limitations).

| use case | tasks generated | test tasks run | kept after the audit |
|---|---|---|---|
| Invoice extraction | 150 | 100 | 91 |
| Insurance claims triage | 150 | 100 | 74 |
| KYC document checks | 150 | 100 | 86 |
| Contract clause review | 150 | 100 | 72 |
| SQL analyst | 135 | 100 | 70 |
| Sales lead qualification and follow-up email | 150 | 100 | 75 |
| IT access requests | 168 | 100 | 87 |
| Pull-request review | 160 | 100 | 74 |
| Meeting notes to CRM | 132 | 100 | 85 |
| Support tickets (private, not included) | n/a | 100 | 100 |
| **all ten** | | 1,000 | 814 |

These counts are regenerated by `scripts/check_tasks.py` (verified 2026-10-22). The test set is the first 100 tasks of each use case in id-hash order. Tasks ranked 101-120 are a development sample, used only to tune the pre-action check.

**Models.** All prices are list prices recorded in `harness/models.py`.

- Closed: Claude Opus 5.5, Sonnet 5.5 and Haiku 5.5; GPT-6 Astra, GPT-6.1 Sol and GPT-6 Luna.
- Open-weight, each on two providers (`provider-a`, `provider-b`): DeepSeek V4.1 Flash, DeepSeek V4 Pro (0813), GLM 5.3, GLM 5.3 Flash and gpt-oss-120b.
- Open-weight, on one provider: Qwen3.8-27B, MiniMax-M3 and Kimi K3.
- Open-weight, on part of the grid only: DeepSeek V4.1 Flash 1017, Muse Spark Open and Beam-1.0.

All settings were vendor defaults. Claude used prompt caching on the system prompt, the tools and the latest turn. GPT-6 models used the Responses API, with their reasoning passed back between turns.

**Conditions.**

- `none`: the agent alone.
- `jev`: v1 of a pre-action check (Jev) on every state-changing call. It sees the last 12 lookups, cut to 1,500 characters, and blocks at p > 0.5.
- `jev3`: the final check. It sees every lookup in full, uses neutral criteria from the written policy only and blocks at p > 0.8. It was tuned on the development sample.
- `nonerz`: the agent alone, with reasoning passed back between turns. This was a robustness check.

**Metrics.**

- Success: the deterministic grade.
- Cost per successful task: every model call's tokens at list price, including cached-input pricing, retries and the extra calls that blocked actions cause.
- Hidden-rule break rate.
- p50 and p95 latency per task.
- Failure types: empty reply, tool-call parse error, step limit, no tool use and refusal. All of these count as unresolved. Only provider API errors are excluded and re-run.

Comparisons are paired over the same tasks, with stratified bootstrap 95% intervals (`harness/report.py`, 3,000 resamples, seed 1).

**The audit.** Three Claude subagents read 270 failed records and rebuilt each task. Based on what they found, 186 of the 1,000 test tasks are excluded identically for every model:

- gold or grader errors;
- 13 hidden rules that the written policy contradicts or that no model could infer;
- task data that varied with Python's hash seed.

`harness/audit.py` documents each exclusion and regenerates `audit_exclusions.json` byte for byte (verified 2026-10-22). The tables are produced on both the audited set and the full set.

## Trust status

**Checked by running, on 2026-10-22, from this directory:**

- All nine `envs/<name>/validate.py` pass. In each, the oracle scores 1.0, the do-nothing agent scores 0.0 and the adversarial checks fail as intended.
- `harness/audit.py` regenerates `audit_exclusions.json` byte-identical.
- `scripts/check_tasks.py` rebuilds every task set. Its fingerprints match the tasks built from the original research directory under `PYTHONHASHSEED=0`. Seven lead-qualification test tasks still change with the hash seed, and all seven are excluded by the audit. The kept counts (91, 74, 86, 72, 70, 75, 87, 74, 85, plus 100 support tasks = 814) match the internal export.
- `harness/grid.py --dry` schedules 189 jobs. That is the original grid minus the support queue.
- Tables from the withheld rows (done privately, not reproducible here): the ported `harness/report.py` was run on the private result rows with the provider labels applied, and the regenerated `results.csv` and `tables.md` match the originals number for number once the labels are mapped back; only the order of rows whose sort key ties (the same model on both providers) and the two provider-naming sentences differ. After the provider rename, one tie-break in the price-matched table changed; `report.py` now breaks ties on success by lower cost per success, which reproduces the original choice. See RERUN.md, "Changes from the original run".

**Not checked:**

- No paid run was repeated, and there is only one run per task. In a check on 159 tasks that changed one setting, 18 tasks flipped (11 up, 7 down), which points to real per-task run noise.
- The audit was done by Claude subagents, not by humans. No human agreement rate exists.
- Claude subagents wrote the environments and the hidden rules, and Claude models did best on hidden-rule tasks, so authorship bias is possible. No second author family has written rules.
- The provider-a prices are unverified (its price page needs a login). provider-a cached input is assumed to bill at the full input price.

**Known inconsistencies between the internal write-up and the data**, from the internal export:

- The draft says the Jev check ran on six use cases. The records pair on five (invoice, KYC, lead, IT access, PR review). The claims-triage Jev runs used the superseded nondeterministic generator and were not re-run.
- The reasoning pass-back check is reported as 71.9% to 74.4% on 160 tasks. With the API-error task excluded, as the harness rule says, it is 115/159 to 119/159.
- The draft says the full set is "about 10-12 pts lower" for every model. The data gives 8.9 to 13.7 pts, and one pair of open models swaps rank on the full set.
- The draft says parse errors, empty replies and step limits are rare except for one model on one provider. No-tool-use endings are also common for gpt-oss-120b on the other provider and for Muse Spark Open.
- The decoy-slice grader problem is described as affecting "26 tasks". `audit_exclusions.json` lists 23 across the generated set, 12 of them in the test set. `audit.py`'s docstring still says claims triage is "excluded as a whole", but the re-run on the fixed generator is included (74 tasks).
- Claude's support (tau2) rows record no cached tokens, so their support cost is at full input price.
- The plan said Kimi K3 would run on 3 use cases and GPT-6 Astra not at all. Both ran on all 10.

**Steps that would vet it further:**

1. Rerun the smoke subset (KYC and PR review, 20 tasks each) on Haiku 5.5 and one open model on each provider, and compare per-task grades with the private rows. Expect flips at about the rate above, not systematic shifts.
2. Hand-check 30 graded failures per environment, including the 270 the subagents read, with a human reviewer, and record agreement.
3. Have a non-Claude model family write a second set of hidden rules for three environments and re-run the hidden-rule split.
4. Confirm the provider-a prices from its console and recompute cost per success.
5. Repeat 3 runs per task for four models on two use cases, to measure run-to-run noise directly.
6. Share each provider's numbers with that provider privately, then publish `results/haiku-tax.json` and the per-task rows.

## Harbor status

`portable`. Nothing is ported yet. Under the Harbor-native target in [STANDARD.md](../../STANDARD.md), porting would take the following.

- **Tasks.** Generate one Harbor task directory per test task (`instruction.md` = the request, `task.toml`, `environment/`, `solution/solve.sh`, hidden `tests/`) from the existing generators with their fixed seeds. The 186 audited-out tasks would be dropped or tagged.
- **Tools as an MCP server.** Serve each environment's read and write tools from an MCP server that runs next to the agent and logs every write to a file. This is the way Harbor's tau3-bench adapter serves tau tools. The written policy goes into the instruction or a mounted file. The hidden rules stay in the grader only.
- **Grader.** `tests/` would load the write log and call the existing `ENV.grade()`. It already scores recorded writes, never prose.
- **Four checks.** Two exist already as code: the oracle (each `validate.py`'s `oracle`, which becomes `solve.sh` calling the MCP tools) and do-nothing = 0. The shortcuts that must score 0 are the existing adversarial checks. A different valid solution still has to be written per environment.
- **Agent.** The runner's own loop (`harness/run.py`: Anthropic Messages, OpenAI Responses and OpenAI-compatible chat, 30 steps, an `ask_user` stub) would become a custom agent (`import_path`), with the Jev arms as an option of that agent. Standard harnesses could then run the same tasks with the MCP server.
- **Support.** The support use case already ran on tau2. It would follow the tau3-bench pattern with a simulated user, but its tasks are a private split.
- **Footguns to plan for.** Write tools must stay non-executing. The hash seed must be pinned when generating tasks. Provider API errors must be counted apart from model failures.

## Limitations

- Synthetic tasks in simulated environments, generated from templates. Phrasing repeats across tasks in some environments (meeting notes, PR review).
- One run per task, so run-to-run variance was not measured.
- Graders are all-or-nothing: one wrong field or one extra write fails a task even when the main decision is right.
- Hidden prudence rules are the most subjective part. After the audit, 18 of 31 rules in the nine harness environments remain, and the hidden-rule analysis rests on 174 tasks.
- The support use case needs the private SwapBench hidden split (tau2-bench bank set, Haiku 5.5 as the simulated customer) and its runner, `support_tau2.py`. Neither is in this repository, so a public rerun covers nine of the ten use cases, and pooled numbers will not equal the original ten-use-case pools.
- Costs are list prices applied to recorded tokens, not invoices. The provider-a prices are unverified.
- Model availability is a snapshot. Gemini was not run (no key) and neither was Claude Fable 5.1 (cost). Several open models were unavailable on the usable providers.
- Latency depends on the per-provider concurrency (8 or 4 workers), so it is indicative only.
