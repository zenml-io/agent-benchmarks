# ml-training-ops: can agents do ML training operations?

## Question

Can agents do ML training operations (distributed jobs, checkpoints, OOMs, stragglers, Kubernetes quotas, torchtitan), and does the serving setup of a self-hosted model change how many they solve?

## Status

Stopped on 2026-10-13. Building frontier-hard tasks stopped because, across five rounds (v1, v2, v3, titan-fork-drift, titan-silent-divergence), Codex with OpenAI models solved 88-100% of every round, so the tasks have no headroom as a frontier capability test. The self-hosted result stands: on the same tasks a 27B open model's solve rate moves with GPU, load and serving settings. Runs: self-hosted on 2026-10-10, 12 and 13; vendor-API runs on 2026-10-12 and 13.

Spend (no exact total exists for this benchmark): vendor-API cost $29.2653 (OpenAI $29.2477, Anthropic $0.0176; token counts x the price table in `src/api_runs.py`, or the harness's own figure when higher; their sandboxes not included). Self-hosted, valid runs: GPU run time $94.0053, startup $8.14, estimated sandboxes $56.8279, which under-counts (see Trust status: re-priced at the tasks' requested CPU and memory it is $223.0465). Partial Modal bills recorded during the runs: $28.35 for Oct 10 13:00-15:00 UTC and $186.20 for Oct 12 (complete hours only, GPU and sandboxes).

## The tasks

24 tasks in Harbor format, each an injected fault in a multi-process training setup, graded by a hidden test that recomputes results (retrains, re-runs with fault injection or hidden seeds, compares to golden loss curves) rather than reading the agent's report.

| round | tasks | source |
|---|---|---|
| v1 pilot (6) | nan-loss, label-shuffle, resume-checkpoint, oom-grad-accum, ddp-sharding, eval-mode | `tasks/mlops_tasks/` (generated by `make_tasks.py`); CPU, 2 CPUs / 4 GB, 20-min agent limit |
| hard set (8), two per family | A distributed jobs: ddp-replica-drift, uneven-shard-hang; B diagnosis from telemetry: straggler-diagnosis, corrupt-shard; C checkpointing: atomic-checkpoint, reshard-optimizer; D resources/scheduling: k8s-unschedulable, memory-leak-oom | `tasks/mlops_hard/src/` (assembled into Harbor tasks by `build.py`); CPU, 4 CPUs / 8 GB, 30-min limit |
| v2 (3 new + atomic-checkpoint) | exact-resume, k8s-quota-zone, two-stragglers | same |
| v3 (5), designed to be hard for frontier models | regression-bisect, throughput-sla, ray-exactly-once, gang-controller, elastic-churn | same; only run with vendor-API agents |
| real-system (2) | titan-fork-drift, titan-silent-divergence | a faulted fork of torchtitan v0.2.2 cloned at image build; 2x L40S, 8 CPUs / 32 GB, 60/90-min limits; only run with vendor-API agents |

Task lists: `data/tasks_mlops.json` (v1), `data/tasks_mlops_hard.json` (hard 8), `data/tasks_mlops_hard2.json` (v2 4), `data/tasks_mlops_all.json` (hard + v2, 11; the v3 and titan API runs used it with one `--tasks` name each).

## Trust status

**Reproduced from the published rows and task sources (2026-10-22):**

- Every value in `results`, `per_type`, `excluded_runs`, `paired_comparisons` and the recorded spend figures of `results/ml-training-ops.json`: `scripts/rebuild_export.py` prints `ALL MATCH`. The paired comparisons read per-task solves from the rows; before publishing, these were checked equal to the raw `reward.txt` files for all 38 valid self-hosted runs.
- The original generated `mlops_hard.md` regenerates byte-identical from the rows (`src/mlops_hard_analysis.py`).
- The task sources rebuild the Harbor tasks used in the runs: `tasks/mlops_hard/build.py` produces files identical to the original built `tasks/` (apart from three empty directories and the `ray-exactly-once` data shards, which the task's own generator recreates byte-identical at image build; verified); `make_tasks.py` regenerates the six v1 tasks identically.
- All 24 task directories load with Harbor 0.24.0's own task loader, and every task named in the four task lists exists (`scripts/validate_tasks.py`).
- Local fault checks without containers (`build.py --check`, `make_tasks.py --check`): for all 16 CPU tasks of the hard, v2 and v3 rounds and all 6 v1 tasks, the original code fails its hidden tests and the reference fix passes (`throughput-sla`, a timing test, needed an idle machine; RERUN.md section 5).

**Not reproduced:** no agent run was repeated. The Modal oracle / no-op validations of the original runs were not re-run (they need Modal sandboxes). The torchtitan tasks need 2 GPUs and were not checked locally. `hard_trace_signals.md` needs the raw trajectories (not published).

**Found while porting:**

- The self-hosted sandbox estimate under-counts by about 4x for these tasks: `experiment.py` looks up a task's CPU and memory in Harbor's registry cache and falls back to 1 CPU / 2 GiB for local tasks, but the hard, v2 and v3 tasks request 4 CPUs / 8 GB (v1: 2 / 4). Re-priced from the recorded sandbox lifetimes at the requested resources, the estimate is $223.0465 instead of $56.8279, so every self-hosted `cost_per_correct_cents` in the export is too low (the GPU part, `gpu_only_cost_per_correct_cents`, is right). The published JSON is left as computed; `scripts/rebuild_export.py` prints the re-priced figure.
- The original repository's `.gitignore` excluded `*.log`, so five task inputs the agents read (`logs/*.log` in atomic-checkpoint, corrupt-shard, memory-leak-oom, reshard-optimizer, uneven-shard-hang) were never committed there; they were taken from the working tree that built the tasks, and the rebuilt tasks match the ones that ran.
- One task input (`uneven-shard-hang/app/logs/nightly.log`) contains the build machine's file paths in a traceback; it is kept as the agents saw it.

**Known inconsistencies (from the export):**

- BENCHMARKS.md (original repo) says the hard set and v2/v3 total "18 tasks incl. titan"; there are 18 task directories in `mlops_hard`, so with the 6 v1 tasks the benchmark has 24.
- Two OpenAI runs over the same 11 tasks have job names tagged `mlops_hard2` and `mlops_hard` but task set `mlops_all` in the rows; both ran all 11 tasks (pooled).
- The original plan's frontier table and "every OpenAI model solves 88-100%" omit the Anthropic runs (0/8 setup failures; 1/2 partial).
- The plan (Oct 10) reports +29 points (CI 8-50) for mini-swe-agent at 8 vs 24 agents from single runs; after repeats the data give +25.
- The plan says mini-swe-agent gains "+6 points, CI [-6, +19]" from 60 minutes; the data give +6 [-2, +17].
- The summary "serving setup moves a 27B model's solve rate 15-25 pts" understates the v2 set, where the H200 effect is +37.5 points for both harnesses.
- Total spend is not separable from the rest of the project.

**Steps that would vet it further:**

1. Run the free Harbor checks on Modal for every task: `-a oracle -k 5` must score 5/5 and `-a nop` 0 (only oracle 1x and nop 1x were recorded, and v3 no-op runs were not recorded).
2. Write and run one shortcut per task that must score 0 (for example, writing `/logs/verifier/reward.json` directly, or editing the test-visible outputs without fixing the job), since only three hard tasks had a partial-fix check.
3. Rerun the headline cell pair (terminus-2 and mini-swe-agent, H100 defaults vs H200 at 24 agents, hard set, 3 attempts per task; recorded $1.57-4.11 GPU per run) and compare the paired differences with +22.92 / +18.75 points.
4. Hand-read the 17 trials where mini-swe-agent's defaults runs at 24 agents failed and classify them (time-out while working, wrong fix, harness error), since the self-hosted failure classes here come only from Harbor exception types.
5. Pull the Modal bills for 2026-10-10/12/13 to replace the estimated sandbox cost with billed cost.
6. Rerun one vendor-API round with the harness versions pinned (`codex` 0.162.1 and `claude-code` 2.1.296 were installed in the original runs, unpinned) to see whether the Anthropic setup failure reproduces.

## Harbor status

`native`. Every trial ran as a Harbor 0.24.0 job on Modal sandboxes against local task directories: self-hosted runs through `../self-hosted-agents-harness/experiment.py` (`harbor run -y -p tasks/mlops_hard/tasks -a <terminus-2 | mini-swe-agent> -m openai/agent-model -e modal -n <agents> -k <attempts> -i <task> ...` against our vLLM server), vendor-API runs through `src/api_runs.py` (`harbor run -y -p tasks/mlops_hard/tasks -a <codex | claude-code | terminus-2> -m <openai/... | anthropic/...> -e modal -n <N> -k <attempts> --ek sandbox_timeout_secs=7200 -i <task> ...`). Tasks use Harbor's format (`instruction.md`, `task.toml`, `environment/Dockerfile`, `solution/solve.sh`, hidden `tests/` with `test.sh` writing `/logs/verifier/reward.txt`).

Distance to this repo's Harbor-native target:

- Four checks: partly done. Oracle passed once per task on Modal (hard 8/8, v1 6/6, v2 4/4 after a fix to exact-resume (the first oracle run scored 2/3 on the then-new tasks), v3 and torchtitan 1-2 runs each); no-op scored 0 on v1, hard, v2 and torchtitan (v3: not recorded). Not done: oracle 5/5, listed shortcuts scoring 0 (only three hard tasks had a partial-fix check), a second valid solution per task. The local `--check` mode is a grader test for "original fails, reference passes" only.
- Grader robustness: `test.sh` writes the reward on every path (no `set -e`), but does not clear `/logs/verifier` first, so an agent that wrote its own `reward.json` there would win over `reward.txt`. Tests are hidden from the agent (copied in after it finishes).
- Base image: one shared `python:3.11-slim` + CPU torch 2.5.1 Dockerfile template; torchtitan tasks install `torchao` and torchtitan's requirements unpinned at build.
- Setups as config: no. Harness, model and serving config are CLI flags; Codex and Claude Code versions were not pinned (0.162.1 and 2.1.296 were installed).
- Publishing: no `dataset.toml` or `registry.json`; tasks run with `-p` from this directory. The hard tasks must be built first (`build.py`).
- Reading results: self-hosted runs have 3-6 attempts per task and the baseline repeated; vendor-API rounds have 1-3 attempts, and the v3 / torchtitan rounds were run one task at a time.

## Limitations

- Small task sets (6, 8, 4, 5, 2); bootstrap CIs over 4-8 tasks are wide.
- The tasks were built by the same team that ran the agents, and later rounds were designed after seeing earlier results; no held-out split.
- One self-hosted model family (Qwen3.8-27B, plus one MoE run per harness) on one engine (vLLM 0.31.0); v3 and torchtitan tasks were only run with frontier API models.
- Frontier coverage is mostly OpenAI models through Codex; the Anthropic runs failed in setup or were aborted and say nothing about Anthropic models.
- API cost excludes Modal sandboxes (including the 2-GPU sandboxes of the torchtitan tasks); OpenAI prices come from third-party aggregators.
- The 4k/16k output caps and the MoE model are single runs.
- Self-hosted failure categories come from Harbor exception types and do not separate looping from working time-outs.
- Sandbox cost for self-hosted runs is an estimate that under-counts by about 4x (above).
- Not published: trajectories, Harbor logs and vLLM metric samples (private archive). Rows keep per-trial outcome, timing, steps, tokens, exception and cost.
